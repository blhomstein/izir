# ADR 0002: Employment source registry boundary

- Status: Accepted
- Date: 2026-09-13
- Ticket: KAN-12

## Definition

An `EmploymentSource` is a registered and independently schedulable acquisition
configuration that selects deployed adapter logic and supplies the validated,
non-secret configuration that logic needs to obtain employment observations from
one provider for one Organization. It is not discovery evidence, an unresolved
candidate, a remote website identity, adapter code, a run, run health, raw data,
or a normalized job.

## Minimal stored model

| Field | Purpose | Nullable | Enforcement |
| --- | --- | --- | --- |
| `id` | Stable internal identity | No | UUID primary key; generated by the application |
| `organization_id` | Employer tracked by this source | No | Foreign key with restricted deletion |
| `name` | Human-facing operational label | No | Trimmed, non-blank, at most 255 characters |
| `adapter_key` | Selects deployed acquisition and configuration logic | No | Application enum and database allowlist |
| `config` | Adapter-specific, non-secret acquisition settings | No | JSON object in the database; strict versioned adapter validation on write/read |
| `config_schema_version` | Selects deterministic config validation | No | Positive integer; supported version checked by adapter |
| `enabled` | Whether new acquisition work should be scheduled | No | Boolean, default `true` |
| `created_at` | Registration time | No | Database default |
| `updated_at` | Last source-record change time | No | Database default; future updates must maintain it |

An Organization can have at most one source for each adapter. The source's UUID
is its stable identity; provider configuration is not treated as identity.

The first deployed registration adapter is Greenhouse configuration schema v1:

```json
{ "boardToken": "acme" }
```

Unknown config fields are rejected.

## Required invariants

1. A source references an existing Organization. An unresolved discovery is not
   registrable.
2. Adapter configuration is valid for the exact `(adapter_key,
   config_schema_version)` on both persistence ingress and egress.
3. `(organization_id, adapter_key)` is unique.
4. `enabled` is scheduling policy only; execution and health do not alter it.

The database enforces structural integrity, the required Organization foreign
key, controlled adapter values, and duplicate registration. The domain/adapter
boundary enforces strict config shape and
supported versions. The repository repeats that validation before writes and
after reads so manually changed or legacy rows cannot reach acquisition logic
unchecked.

## Duplicate registration decision

Izri currently tracks at most one source for each provider used by a company.

- Registering a second Greenhouse source for one Organization is a duplicate.
- A Greenhouse source and a future Lever source for one Organization are distinct.
- Two Organizations can each have a Greenhouse source, even when their provider
  configuration happens to match.
- Supporting multiple accounts or feeds for one company and provider is deferred
  until that requirement exists.

## Deliberately excluded

- `source_kind`: no current policy, invariant, or behavior consumes the taxonomy.
- `acquisition_method`: currently implied by adapter implementation.
- universal URL fields: Greenhouse access is derivable from its board token;
  observed URLs belong to discovery evidence.
- discovery evidence, candidates, and provenance: inputs to resolution, not
  registered acquisition state.
- status/health/run fields: belong to `IngestionRun` or a later health projection.
- schedule, retries, counters, crawler state, raw payloads, and normalized jobs:
  belong to later scheduling, execution, observation, or normalization models.
- secrets: config may eventually carry secret references, never secret values.
- config migration framework: version is stored, but no incompatible version
  exists to migrate yet.
- archive/retirement: no current requirement beyond `enabled`.

## Consequences

Adding an adapter requires deployed code, a controlled-key database migration,
strict config validation, and tests. Adding Lever, generic HTTP API, generic
HTML, or browser-backed acquisition is therefore intentionally deferred until
its real configuration and behavior are known.

Supporting more than one source per Organization and adapter will require an
explicit identity rule when that need becomes concrete.
